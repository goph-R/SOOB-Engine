# Building FLTK for the SOOB Level Editor on Windows 98

The SOOB level editor (`editor/editor.cpp`, built by `build_editor.bat` at the
repo root) uses **FLTK** for its window + GL viewport. FLTK does not ship a Win98 binary, so you build it
yourself, once, with the same Dev-C++ MinGW 3.4 toolchain the engine uses. This
doc is that recipe.

## Which version

| Use | Avoid |
|---|---|
| **FLTK 1.3.11** (latest 1.3.x) | **FLTK 1.4+** — requires C++11, which Dev-C++ GCC 3.4 can't do |

FLTK 1.3.x is C++98/03 and builds with old MinGW. FLTK's *official* platform
floor is Windows 2000+ (since 1.3.0), so Win98 is "not officially supported but
works" — the codebase is right, but Win98 is enabled by build-time config, not
by default. If 1.3.11 errors on GCC 3.4, drop to an earlier 1.3.x (the 1.3.3–
1.3.4 era has the most "built with ancient MinGW" reports). Nothing in
`editor.cpp` uses recent FLTK API, so an older 1.3.x is a drop-in.

## The three things that make it work on Win98

1. **Build at `-DWINVER=0x0500 -D_WIN32_WINNT=0x0500`.** This is counter-intuitive
   — you'd expect the Win9x level (`0x0400`) — but FLTK 1.3.11's `Fl_win32.cxx`
   references a handful of Win2000+ symbols *at compile time* (`XBUTTON1` /
   `GET_XBUTTON_WPARAM` for extra mouse buttons; `BITMAPV5HEADER` in
   `image_to_icon` for alpha window-icons and RGB cursors), so `0x0400` won't
   compile. Building at `0x0500` only makes those symbols *declared* — the win32
   backend has **no version-gated `#if` blocks**, so no new runtime code is
   enabled, and both sites are **dead code at runtime for the editor** (Win98
   never sends `WM_XBUTTON*`, and the editor sets no `Fl_RGB_Image` icon or
   custom cursor). The underlying functions (`CreateDIBSection`, `TrackMouseEvent`,
   `LoadIcon`, …) all exist on Win98, so nothing becomes an unresolvable import —
   the binary still loads and runs on Win98. (`BITMAPV5HEADER` is gated on
   `WINVER`, not `_WIN32_WINNT`, which is why *both* must be raised.)
2. **Same toolchain, static libs** — build FLTK with the *same* Dev-C++ MinGW
   3.4 used for the engine, producing static `libfltk.a` / `libfltk_gl.a` (ABI +
   CRT match, no DLL surprises). `build_editor.bat` links these statically.
3. **Core libs only — skip `fluid` and the test/example programs.** Those pull
   in Win2000+ calls (e.g. `GetFileSizeEx` in fluid's code editor). The FLTK
   *library* core is fine on Win98; the editor never needs fluid.

## Vendored FLTK patch (SDK back-fill shim)

Raising the API level to `0x0500` isn't enough on Dev-C++'s MinGW 3.4: its
bundled w32api is old enough that a few Win2000-era GDI declarations simply
**aren't in the headers at any `WINVER`**. So `build_fltk.bat` builds at
`0x0500` *and* the vendored FLTK carries a small compat shim:

- **`vendor/fltk-1.3/FL/src/fl_win98_compat.h`** (new file) — guarded
  definitions for the symbols the old SDK lacks:
  `XBUTTON1` / `XBUTTON2` / `GET_XBUTTON_WPARAM` (extra mouse buttons),
  `BITMAPV5HEADER` (alpha icons/cursors), and `GGI_MARK_NONEXISTING_GLYPHS` /
  `GGO_GLYPH_INDEX` (the `GetGlyphIndicesW` text path). The `#ifndef` guards
  make it a no-op on a newer SDK.
- Two one-line `#include "fl_win98_compat.h"` additions:
  `src/Fl_win32.cxx` and `src/fl_font_win32.cxx` (each already has `windows.h`
  in scope via its dispatcher, so the base types the shim needs exist).

Every shimmed symbol is **dead code at runtime on Win98** — the paths that use
them (`WM_XBUTTON*`, `image_to_icon`, `GetGlyphIndicesW`) never execute there,
and the functions actually called all exist on Win98 — so the binary still
loads and runs. FLTK already handles `WM_MOUSEHWHEEL` and `DwmGetWindowAttribute`
itself (local `#define` / `GetProcAddress`), so those needed nothing.

**These three files are part of the editor's build and must survive if you
re-extract FLTK.** They live inside `vendor/fltk-1.3/` and are tracked (only
the built `lib/*.a` and `raw/obj/fltk/` objects are gitignored).

## Not a blocker on Win98

You'll see `InterlockedExchangeAdd` cited as a Win9x failure in FLTK threads —
that's a **Windows 95** problem. Windows 98/98SE has that symbol (it arrived
with 98 / NT4), so those Win95 reports don't apply to you.

## Build steps (no configure / CMake / MSYS needed)

The editor ships a `build_fltk.bat` that compiles FLTK's static libs directly
with the Dev-C++ toolchain — the same batch style as `build.bat`. It does the
Win98-specific setup for you (the three points above), so you don't run FLTK's
own build system at all.

1. **Put the FLTK 1.3.11 source at `vendor/fltk-1.3/FL/`** — i.e. the FLTK root
   (the dir with `src/`, `FL/`, `configure`) lives at `vendor/fltk-1.3/FL/`, so
   headers are `vendor/fltk-1.3/FL/FL/*.H` and sources `vendor/fltk-1.3/FL/src/`.
   Two support files are committed alongside it and must be present:
   - `vendor/fltk-1.3/FL/config.h` — hand-authored (from `ide/VisualC6/config.h`,
     image libs off). Normally generated by configure; supplied so we skip it.
   - `vendor/fltk-1.3/FL/FL/abi-version.h` — also normally generated; defines
     **`FL_ABI_VERSION 10304`** (raised from the 10300 default — see *Local FLTK
     patch: ABI 10304* below). Changing this changes `sizeof(Fl_Text_Display)`,
     so FLTK and everything linking it must be rebuilt together.
   - `vendor/fltk-1.3/fltk_core.list` / `fltk_gl.list` — the exact source lists,
     extracted from FLTK's own Makefile (only the cross-platform dispatcher
     `.cxx`; the `_win32` backends are `#include`d by them, not compiled alone).

2. **Run `build_fltk.bat`** from the engine root. It compiles the two lists with
   `-DWIN32 -D_WIN32_WINNT=0x0400 -DFL_LIBRARY` and archives
   `vendor/fltk-1.3/FL/lib/libfltk.a` + `libfltk_gl.a`. It skips `fluid` and the
   test/example programs entirely (they need Win2000+ APIs; the library core
   doesn't). Delete `raw/obj/fltk` to force a rebuild.

If a single file breaks on GCC 3.4, note which one — late 1.3.x patches
occasionally need a small tweak on the old compiler. (The alternative route,
if you'd rather: install CMake + `mingw32-make` and configure with
`-DFLTK_BUILD_FLUID=OFF -DFLTK_BUILD_TEST=OFF -DOPTION_BUILD_SHARED_LIBS=OFF`
and `-D*_FLAGS="-DWINVER=0x0500 -D_WIN32_WINNT=0x0500"`.)

## Then build the editor

Run `build_editor.bat` from the **repo root** (where it lives), so you build and
run `SoobEditor.exe` from the same folder. Its `FLTK` variable points at
`vendor\fltk-1.3\FL`, and it errors early if `build_fltk.bat` hasn't produced the
libs yet. It compiles `editor\editor.cpp` with `-DWIN32 -I. -I%FLTK%` (the `-I.`
picks up the engine-root headers the editor includes by bare name; the editor's
own `edit_*.h` resolve next to `editor.cpp`) and writes `SoobEditor.exe` to the
repo root. It links
`-lfltk_gl -lfltk` plus Bullet, Lua, and Win32 GL/GDI. No SDL, OpenAL, or
vorbis — the `game.h` / `game_session.h` split keeps the script/UI/audio
runtime out of the editor TU. Lua alone is linked, only so `edit_assets.h` can
run `assets.lua` in a bare Lua state and register the `models`/`textures` the
entities reference (mesh=/iqm=/tex=). (`-mwindows` is intentionally omitted so
the editor's `conLogf` stdout stays visible while bringing it up.)

Run `SoobEditor.exe` from the repo root — assets are relative-pathed, exactly
like the game.

## Related

- `editor/editor.cpp` — the editor skeleton (free-fly camera, grid + axis
  overlay); all editor code lives under `editor/`, separate from the game TU.
- `editor/edit_mesh.h` / `edit_mesh_build.h` — the editor's native mesh and its

  can be included without the script/UI/audio runtime.

## Local FLTK patch: Unicode window APIs on Windows 9x

**This is the one that matters. Re-apply it if FLTK is ever upgraded.**

FLTK 1.3 creates its windows through the Unicode Win32 entry points:

```c
RegisterClassExW(&wcw);            // Fl_win32.cxx
x->xid = CreateWindowExW(...);
```

Windows 95/98/ME implement those as stubs that fail. `CreateWindowExW` returns
NULL, so `x->xid` is NULL — yet `Fl_X` still exists and `shown()` still returns 1,
so nothing reports a problem. FLTK 1.3 effectively requires Windows 2000 or later.

Everything observed on the Win98 box follows from that single fact:

| Symptom | Cause |
|---|---|
| No window, no splash, no menu bar | HWND is NULL |
| `draw()` never runs, so `bootstrap()` never runs | no HWND means no `WM_PAINT` |
| `wglCreateContext` fails, `ERROR_INVALID_HANDLE` | `GetDCEx(NULL, ...)` returns NULL |
| `Multitexture: not available` on an MX440 | there is no GL context |

`fl_is_win9x()` in `Fl_win32.cxx` detects the platform once at runtime, and the
window class registration, `CreateWindowEx`, `DefWindowProc`, `SetWindowText`,
`RegisterWindowMessage` and the message pump each branch to their `A` variants on
9x. The A and W entry points **must** be used consistently — a class registered
with `RegisterClassExA` whose messages go to `DefWindowProcW` decodes characters
at the wrong width. Detection is at runtime, not compile time, so one binary still
works on NT. Window labels degrade to ANSI on 9x, which that platform could not
have rendered anyway.

## Local FLTK patch: ABI 10304 (line-number colours)

**Re-apply if FLTK is ever upgraded.**

`Fl_Text_Display`'s line-number margin accessors — `linenumber_bgcolor()`,
`linenumber_fgcolor()`, `linenumber_font()`, `linenumber_size()`,
`linenumber_align()`, `linenumber_format()` — are 1.3.3 *ABI* features. At the
default ABI of 10300 the backing members don't exist:

```c
// FL/Fl_Text_Display.H
#if FLTK_ABI_VERSION >= 10303
  Fl_Font     linenumber_font_;
  Fl_Color    linenumber_bgcolor_;
  ...
#endif
```

so the setters compile to **nothing** and the getters return hard-coded values —
`linenumber_bgcolor()` literally `return 53; // hard coded ~90% gray`. The code
editor's margin therefore rendered light grey no matter what colour it asked
for, with no warning at compile time or runtime.

`FL/abi-version.h` now defines `FL_ABI_VERSION 10304`. `Enumerations.H` maps
that onto the deprecated `FLTK_ABI_VERSION` and clamps anything above
`FL_API_VERSION` (10311 here), so 10304 is legal. This is the mechanism FLTK
documents in `README.abi-version.txt`.

**This changes `sizeof(Fl_Text_Display)`.** Rebuild the WHOLE library and
everything that links it:

```
rmdir /s /q vendor\fltk-1.3\FL\lib
rmdir /s /q raw\obj\fltk
fltk98
ed98
```

### The mixed-ABI trap

`fltk98.bat` guards every compile individually:

```
if not exist ..\lib\o\Fl_Text_Editor.o %DC%\g++.exe ... -c Fl_Text_Editor.cxx ...
```

so deleting *some* objects and rerunning it yields a library whose objects were
built at **different ABI levels**. That is worse than not rebuilding at all,
because the symptoms are silent and local rather than obvious.

What it cost us: the code editor crashed on File / Close, every single time,
while everything else — including the line-number colours the ABI bump was for —
worked perfectly. The mechanism:

| | compiled into |
|---|---|
| `Fl_Text_Editor` **constructor** (`Fl_Text_Editor.cxx:71`) | `libfltk.a` |
| `Fl_Text_Editor` **destructor** (`Fl_Text_Editor.H:54`, inline) | **the application object** |

At 10304 `Fl_Text_Display` gains six members, shifting everything below them —
including `Fl_Text_Editor::key_bindings`. With `Fl_Text_Display.o` rebuilt (so
the colours worked) but `Fl_Text_Editor.o` stale, the constructor wrote
`key_bindings` at one offset and the inline destructor read it 24 bytes further
on: `delete` on a garbage pointer, on every widget destruction.

An inline destructor paired with a library constructor is what turns an ABI
mismatch from merely wrong into fatal, and `Fl_Text_Editor` has exactly that
shape.

**So: any change to `FL/abi-version.h` means `rmdir /s /q` on the whole `lib`
tree — never a selective delete.** Selective deletes remain fine for ordinary
source edits (see *Rebuilding after touching FLTK source* below); those do not
move struct layouts.

`codeedit.exe` checks for this at startup and alerts if `linenumber_bgcolor()`
returns FLTK's hard-coded `53` instead of the colour it set. That only catches a
stale `Fl_Text_Display.o` — the mixed case above slips past it, so a clean
rebuild is the only real test.

Debugging aid, since this class of bug gives no useful crash information:
`codeedit -trace` writes `codeedit.log` next to the exe, appending and closing
per line so a hard crash still leaves the last one. It was the log showing
`~CodeEditor` completing normally that moved the search into the base
destructors and found this.

## Local FLTK patch: ANSI file I/O on Windows 9x

**Re-apply if FLTK is ever upgraded.** Same root cause as the Unicode window
issue above, in a different subsystem.

Every path helper in `src/fl_utf8.cxx` converts its argument to UTF-16 and calls
a wide CRT function — `fl_fopen` → `_wfopen`, `fl_open` → `_wopen`, `fl_stat` →
`_wstat`, and so on for `_waccess`, `_wgetcwd`, `_wunlink`, `_wmkdir`,
`_wrmdir`, `_wrename`. Windows 95/98/ME implement the wide CRT as stubs that
fail.

The visible symptom was that the code editor **could not open any file at all**
— absolute path, relative path, or a file sitting next to the .exe. `fl_fopen`
returned NULL, so `Fl_Text_Buffer::insertfile` returned 1 ("could not open") for
files that plainly existed, and the editor came up empty.

`fl_utf8.cxx` now carries a file-local `fl_win98_is_9x()` (a differently-named
twin of the `fl_is_win9x()` in `Fl_win32.cxx`, so the two don't collide) and
each of those nine functions takes the plain ANSI call on 9x:

```c
FILE *fl_fopen(const char* f, const char *mode) {
#if defined (WIN32) && !defined(__CYGWIN__)
  if (fl_win98_is_9x()) return fopen(f, mode);   /* SOOB Win98 */
  ... existing _wfopen path ...
```

On 9x the ANSI call is also the *correct* one — that platform's filesystem is
codepage-based, and FLTK's UTF-8 strings are byte-identical to ANSI for the
ASCII paths these builds use. Detection is at runtime, so one binary still uses
the Unicode path on NT.

`<sys/stat.h>` was added to the non-Cygwin WIN32 include branch, since `stat()`
was previously only needed on the other platforms' side.

## Local FLTK patch: ANSI directory listing on Windows 9x

**Re-apply if FLTK is ever upgraded.** Third instance of the same root cause.

`fl_scandir()` in `src/scandir_win32.c` enumerates with `FindFirstFileW` /
`FindNextFileW`. On Windows 95/98/ME those are stubs that fail, so the function
returned a listing of **zero entries** — not an error, just nothing. FLTK's own
file chooser therefore shows every directory as empty, which makes File / Open
useless. (`scandir_win32.c` is `#include`d by `scandir.c`, which is the entry in
`fltk_core.list`, so the object to delete is **`scandir.o`**.)

The file now carries its own `fl_win98_is_9x()` — a third copy, because this is a
`.c` translation unit and cannot share the C++ one in `fl_utf8.cxx` — and picks
the entry points at runtime:

```c
if (use9x) h = FindFirstFileA(findIn, &finda);
else       { ...existing UTF-16 conversion + FindFirstFileW... }
...
} while (use9x ? FindNextFileA(h, &finda) : FindNextFileW(h, &findw));
```

The loop body builds `d_name` from whichever `WIN32_FIND_DATA` is live. On the
ANSI side there is no transcoding to do — `cFileName` is already in the
filesystem's codepage — so it is a `memcpy`, sized `l + 2` for the name, the `/`
that gets appended to directories, and the terminator (`struct dirent` is
`{char d_name[1];}` and is over-allocated, so that is one byte of slack).

**Do not use `Fl_Native_File_Chooser` on Win98.** It is
`OPENFILENAMEW` / `GetOpenFileNameW` / `GetSaveFileNameW` / `SHBrowseForFolderW`
throughout — the whole class is unusable on 9x and is not worth patching. Use
FLTK's own drawn `fl_file_chooser()`, whose other dependencies (`fl_stat`,
`fl_access`, `fl_getcwd` via `filename_isdir`) are already covered by the
`fl_utf8.cxx` patch.

`editor/chooser98.cpp` (built by `f98.bat`) is the probe for this. It checks the
layers separately — `fl_filename_list()` first with no GUI at all, then the
`fl_stat`/`fl_access`/`fl_getcwd` group, then the full chooser — so a failure
says which layer broke. An empty stage 1 that still lists no `.` or `..` is the
signature of this bug.

## Local FLTK patch: line-number margin repaint gate

**Re-apply if FLTK is ever upgraded.** A performance patch, not a correctness one.

`Fl_Text_Display::draw()` ends with an **unconditional** `draw_line_numbers(true)`,
outside every damage check. The history is visible in the source: the
`FL_DAMAGE_ALL` branch still carries `//draw_line_numbers(true); // commented out
STR# 2621 / LZA`. Upstream moved the call out of the damage-gated branches
because gating it on damage stopped the numbers scrolling with the text, and
settled for "always repaint the margin".

`draw_line_numbers()` is not cheap: one `fl_rectf` over the margin's full height
plus an `fl_draw` per visible row. So every keystroke repainted every line
number — clearly visible on the Pentium II.

The digits can only change when the top visible line number changes, so `draw()`
now gates on exactly that plus the damage bits that mean the margin's own pixels
were clobbered:

```c
int soobTop = get_absolute_top_line_number();
if ((damage() & (FL_DAMAGE_ALL | FL_DAMAGE_EXPOSE)) || soobTop != mSoobLineNumTop) {
  mSoobLineNumTop = soobTop;
  draw_line_numbers(true);
}
```

`mSoobLineNumTop` is a new member (initialised to -1 in the constructor), so this
changes `sizeof(Fl_Text_Display)` — another reason FLTK and its dependants must
be rebuilt together.

**Why scrolling still works** — every scroll path funnels through
`Fl_Text_Display::scroll_()`, which ends in `damage(FL_DAMAGE_EXPOSE)`, a bit the
gate already lets through. That covers the mouse wheel (`FL_MOUSEWHEEL` →
`mVScrollBar->handle()` → `v_scrollbar_cb` → `scroll()`), scrollbar dragging (the
same callback), and the cursor walking off an edge (`display_insert()`). The
top-line comparison is the second belt: it catches edits that renumber lines
*without* scrolling, such as a paste above the viewport.
`get_absolute_top_line_number()` is O(1) with wrapping off — it returns
`mTopLineNum` outright — so the gate costs nothing.

**Caveat:** changing a margin setting at runtime (`linenumber_bgcolor()`,
`linenumber_width()`, …) no longer repaints on the next unrelated draw. Call
`redraw()` after changing them. Setting them once at construction, as
`editor/edit_code.h` does, is unaffected.

## Local FLTK patch: GL device context (defensive)

`vendor/fltk-1.3/FL/src/Fl_Gl_Choice.cxx` carries a one-line fallback. It is *not*
what broke the editor — the Unicode issue above was — but it costs nothing and
guards a genuinely fragile call.

FLTK registers its window class with `CS_OWNDC` (`Fl_win32.cxx`). In
`fl_create_gl_context` it then asks for a DC with:

```c
hdc = i->private_dc = GetDCEx(i->xid, 0, DCX_CACHE);
```

On Windows NT `GetDCEx` merely *ignores* `DCX_CACHE` for a `CS_OWNDC` window. On
Windows 95/98/ME it **fails and returns NULL**. FLTK never checks the result, so
`SetPixelFormat` quietly failed on a NULL DC and `wglCreateContext` returned 0 with
`GetLastError() == ERROR_INVALID_HANDLE` (6).

Note the DC being NULL on Win98 was itself a *consequence* of the Unicode problem:
`GetDCEx` was being handed a NULL `xid`. The fallback is kept only because
`GetDCEx` with `DCX_CACHE` is documented as being ignored for a `CS_OWNDC` window
and FLTK never checks the result.

One FLTK behaviour is worth knowing when debugging this area: `Fl_Gl_Window::show()`
answers a missing context by calling `Fl::error("Insufficient GL support")` and
returning **without creating the window** (`Fl_Gl_Window.cxx:77`). `Fl::error`
defaults to stderr, and COMMAND.COM has no `2>&1`, so that message can never reach a
log file on Win98 — `editor.cpp` therefore routes `Fl::error`/`warning`/`fatal`
through `conLogf`.

The patch falls back to `GetDC`, which with `CS_OWNDC` returns the window's own
private DC — the right DC for a long-lived GL context regardless:

```c
if (!hdc) hdc = i->private_dc = GetDC(i->xid);
```

`editor.cpp` also negotiates the GL mode with `Fl_Gl_Window::can_do` rather than
assuming one, routes `Fl::error`/`warning`/`fatal` into `conLogf`, and exits with a
diagnostic instead of hanging if the context is missing.

### Rebuilding after touching FLTK source

`fltk98.bat` skips any source whose object already exists, so editing an FLTK file
is not enough on its own. Delete the object and the build sentinel:

`Fl_win32.cxx` is not compiled on its own — it is `#include`d by `Fl.cxx`, so
editing it means deleting **`Fl.o`**, not `Fl_win32.o`. (`fl_utf8.cxx` *is* in
`fltk_core.list`, so that one does have its own `fl_utf8.o`.) Note that a change
to `FL/abi-version.h` invalidates **every** object, not just one — delete the
whole `lib` and `raw\obj\fltk` trees for that:

```
del vendor\fltk-1.3\FL\lib\o\Fl.o
del vendor\fltk-1.3\FL\lib\og\Fl_Gl_Choice.o
del vendor\fltk-1.3\FL\lib\fltkok.tag
fltk98
ed98
```

`t98.bat` builds `editor/fltktest.cpp`, a small probe that shows a plain
`Fl_Window` and an `Fl_Gl_Window` child and reports whether either paints. It is
the quickest way to tell "FLTK cannot show a window" from "only GL is broken"
without a full editor build.
